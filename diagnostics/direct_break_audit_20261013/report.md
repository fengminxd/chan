# 笔破坏逻辑审查与前次结论更正（2026-10-13）

后续状态：本报告保留针对 v8 的缺陷证据；已在 v9 修复并更新原图表，见[修复与验收](../direct_break_fix_20261013/report.md)。下文“当前／生产”指审查当时的 v8。

**结论：有实质性错误。当前 `direct_break` 把“第一反向笔已经破坏原段”缩窄为“第一反向笔包住旧特征元素”的条件，比较错了区间边界。它既导致漏标破坏笔，也会让后续处理走错分支，出现提前确认或漏确认。**

必须更正前次结论：v8 把“包含后出现缺口”一概作为需要第二特征序列的理由，但没有先正确排除第一笔已经破坏的特殊情况。本次最小反例证明，前次判为错误的部分确认实际不应被撤销或推迟。原 v8 修复报告及其测试预期不能继续作为规则正确的证明。

本轮完成审查与内存隔离试算，**未修改生产算法和 HTML**。下文的试算不是已发布修复；旧报告顶部已补充更正说明。

## 1. 比较错在哪里

位置：[chan_structure.py:132](/root/chan/chan_structure.py:132)。

```python
direct = middle.low <= left.low if direction == "up" else middle.high >= left.high
```

`left` 是旧特征元素，`middle` 是从候选转折开始的第一反向笔。上述条件要求：上涨时反向笔落到旧元素低点以下；下跌时反向笔升到旧元素高点以上。这接近判断包含型关系，遗漏已经进入前面同向笔价格范围的第一笔破坏。

在没有复杂历史包含的最小三笔原段中，正确的边界对应关系是：

| 原段方向 | 第一反向笔 | 破坏比较边界 | 当前误用边界 |
|---|---|---|---|
| 上涨 | 向下笔 | 旧特征元素的**高点** | 旧特征元素的低点 |
| 下跌 | 向上笔 | 旧特征元素的**低点** | 旧特征元素的高点 |

直接代入[第65课](https://chanlun108.cn/chanzhongshuochan108ke/65.html)的指标定义即可验证，而不必依赖本程序：

```text
0 → 8 → 4 → 10 → 6
d1  g1  d2  g2   d3

i = 1，j = 3，j >= i + 2
d3 = 6 <= g1 = 8
```

因此 `10 → 6` 已经是第一笔破坏。它不需要先跌破 `d2=4`。当前代码拿 `6 <= 4` 判断，得到 false。价格镜像后，下跌段同样误判。

本次隔离试算只把比较边界改为：

```python
direct = middle.low <= left.high if direction == "up" else middle.high >= left.low
```

这能验证根因和影响，但本轮没有把它当成“全部笔破坏逻辑的完整修复”。多元素标准化、既往破坏与候选生命周期仍须在正式修复中统一验收，不能把一个简单比较表达式等同于第65课所有历史 `i,j` 关系的完整实现。

## 2. 三个直接反例

### 反例 A：漏标第一笔破坏

```text
0 → 8 → 4 → 10 → 6
```

前三笔是原上段，第四笔 `10 → 6` 已满足破坏条件。此时应记录该笔发起破坏，但不能据此立即确认原段结束。生产程序没有这条 `direct_break` 事件。

图表忠实使用了程序标记，问题在结构判定；不能通过单独把更多线段画粗来修复。后续正式修复仍须保留用户显示规则：只加粗发起破坏的笔，宽 3.2，保留颜色和实线/虚线。

### 反例 B：仅触及首笔终点，却提前确认

```text
0 → 8 → 4 → 10 → 6 → 9 → 7 → 8 → 6
```

首笔破坏为 `10 → 6`。后面的下降端点是 7、6，没有严格跌破首笔终点 6，也没有先突破首笔起点 10。按项目已经采用的“后续笔须严格突破首笔终点”等待规则，此时应继续等待。

生产程序却输出已确认段 `0 → 10`，证据是第 7 号笔。原因是：`direct=false` 误入普通分型分支；包含后形成表面顶分型，反向跨度又允许末端等于最低点，于是绕过了特殊分支中的严格突破条件。

这是内部判据不一致，不仅是图上少了粗线。价格镜像也提前确认。

### 反例 C：首笔破坏已完成后续突破，却错误等待第二序列

```text
0 → 8 → 4 → 14 → 6 → 13 → 9 → 12 → 8 → 11 → 5
```

`14 → 6` 已经破坏旧上段，因为 `6 <= 8`。其后的下降端点 9、8 仍在首笔内部；最后下降至 **5 < 6**，在未先突破 14 的前提下，解决了首笔破坏的等待状态。根据[第71课](https://chanlun108.cn/chanzhongshuochan108ke/71.html)的这条特殊规则，应确认 `0 → 14` 结束。

当前 v8 却输出零条确认段，并报告 `waiting_reverse_feature_fractal`：由于没有识别首笔破坏，程序继续把右侧元素按普通序列合并，得到 `[9,14]`，再用它与左元素 `[4,8]` 比较，产生缺口并要求第二序列。

**这正是前次审查使用过的同一个反例。前次把“等待第二序列”写成正确预期是错误的：漏掉了先判断第一笔破坏这个前提。** 不能仅从包含后的区间出现缺口，倒推出首笔破坏特殊分支不存在。

## 4. 对指定 1h 四段的影响

冻结当前笔序列，仅在独立内存模块改动比较边界。**08-14 22:00 至 09-16 02:00 仍为原来的四段；四段全部字段、端点、证据笔和确认时间一致。** 但前两处分界的具体审计原因与破坏标志发生变化：

| 分界点 | 发起笔 | 破坏比较 | 后续严格突破 | 审计原因变化 |
|---|---|---|---|---|
| 08-25 10:00 | P1595，81,270.5 → 77,808.1 | 77,808.1 ≤ 79,555.5 | P1597：77,600.0 < 77,808.1 | 普通分型 → 第一笔破坏确认 |
| 08-29 00:00 | P1600，76,853.1 → 78,314.9 | 78,314.9 ≥ 77,600.0 | P1602：79,384.4 > 78,314.9 | 普通分型 → 第一笔破坏确认 |

| 09-16 02:00 | P1614 | 未满足本次试算的首笔破坏条件 | 等第二特征序列 | 不变 |

因此必须更正前份 1h 报告中“前两处 `direct_break=false` 可作为正确分类”的解释。数值上的顶、底分型仍存在，但不能以此漏掉首笔已经破坏的事实。两处同时满足后续突破，所以修正分类后几何分段没有变化。

本次没有发现足以凭这个阈值问题把四段改成两段的证据。“反向先破起点后原段延续”本身有第71课依据；问题在于程序是否先正确识别了第一笔破坏，以及是否执行了对应等待分支。
